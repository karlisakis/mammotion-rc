This page shows the raw state PyMammotion holds for the mower — refreshed every 3 s — and can probe which read-only query commands the firmware actually answers over the BLE proxy. The probe never sends anything that moves the mower, spins the blades, or changes a setting. Note that sent-no-change is NOT proof a command is unsupported: some replies land in fields this page does not watch, and an answer identical to the current value produces no visible diff.

Capability probe

Sends 9 read-only queries in sequence (~30 s total), snapshotting the relevant fields before and after each. replied = a watched field changed; sent-no-change = sent but nothing we watch moved (not proof of unsupported); not-in-lib = the installed PyMammotion has no such command; error = sending failed.

Message trace

Taps the decoded inbound BLE stream, sends one curated command, then records every message the mower pushes back for a few seconds. This is what separates the three possibilities for set_blade_height: a driver.toapp_knife_status_change in the timeline means the mower accepted the command and only our read-back is stale; driver traffic without a knife event means it replied but refused; no new traffic at all means it ignored it. Run noop first — that sends nothing, so whatever it captures is the mower’s unprompted background chatter, which is the baseline every other run must be read against. Nothing on the command list moves the mower or spins the blades.
